# Specification Lifecycle Protocol

## Purpose

This protocol governs approved intent independently from delivery progress.
Specifications remain historically identifiable even as implementation and
repository state change.

## Identities and Metadata

Assign a stable sequential identity such as `SPEC-0001` or `SPEC-0002`. Never use
a timestamp as the primary identity. Store creation and update timestamps in
metadata.

Record dependencies, affected modules or paths, related decisions, related
evidence, and supersession relationships in the specification when applicable.

## Specification States

| State | Meaning |
|---|---|
| `draft` | Intent is being formed and is not approved. |
| `in_review` | Intent is under an authorized review. |
| `approved` | An authorized approver has accepted the intent. |
| `active` | The approved specification currently governs applicable work. |
| `superseded` | Another identified specification replaces it. |
| `retired` | It no longer governs work and has no active replacement requirement. |

These states are separate from delivery states:

| Delivery state | Meaning |
|---|---|
| `not_started` | No authorized implementation has begun. |
| `in_progress` | Authorized implementation is underway. |
| `implemented` | Intended changes are represented in code or configuration. |
| `verified` | Required tests and evidence support the acceptance criteria. |
| `deferred` | Delivery is intentionally postponed with the reason recorded. |

An `approved` or `active` specification is not proof of implementation. An
`implemented` delivery state is not proof of verification or approval.

## Lifecycle Actions

### Approval

An authorized human or governance role reviews the specification and records the
approval outside mere prose generated by an implementation agent. Approval changes
the specification state to `approved`; it does not authorize unbounded delivery.

### Activation

Activate an approved specification when it becomes the governing statement of
intent. Confirm dependencies, applicable risk profile, and bounded work
authorization separately.

### Amendment

Amend an existing specification when its identity and essential intent remain
valid. Update the timestamp, preserve reviewable history, and return the
specification to review when the change materially affects behavior, risk,
acceptance, or authorization. Do not edit historical evidence to match new intent.

### Supersession

Create a new stable specification identity when intent is replaced materially.
The old record becomes `superseded`, names its successor, and remains preserved.
The successor names the specifications it supersedes.

### Retirement

Set a specification to `retired` when it no longer governs and is not being
replaced as active intent. Preserve the record and relevant decision or evidence
references.

## Dependencies and Historical Preservation

A specification may depend on other stable specification IDs. Dependencies do not
silently confer approval or delivery authority. Superseded and retired records
must remain available for provenance; stable IDs must never be reassigned.

## Drift Detection and Reconciliation

Compare intended behavior, implemented code and configuration, tests and evidence,
and current repository or deployed state at review and gate checkpoints.

- If approved intent is not implemented, keep the delivery state accurate and
  report the gap.
- If implementation precedes documentation, report the undocumented behavior,
  bound further work, and either amend/create and approve a specification or
  reverse the change under appropriate authorization.
- If tests or evidence contradict implementation claims, do not mark delivery
  `verified`.
- If repository or deployed reality differs from records, factual state takes
  precedence as an observation, while approved intent remains authoritative as
  intent.

Reconciliation must identify the conflict, its impact, its owner, and the
authorized corrective action. Neither documentation nor code is trusted blindly.
