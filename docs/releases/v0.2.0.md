# AFEF v0.2.0

AFEF v0.2.0 defines a minimum-adoption control plane with exactly three
integrated record contracts and schemas: a project manifest, specifications, and
work records. Compact templates help adopters create their own records under
`.afef/`.

The framework includes a narrow deterministic offline conformance validator,
repository-local CI for its validation suite, deterministic valid and invalid
fixture checks, and a synthetic clean-room adoption proof that invokes the real
validator outside the framework checkout and verifies non-mutation. I1, I2, I3,
and the I3-CR1 clean-room strengthening passed their controlled implementation
and review chains.

## Compatibility and Adoption

AFEF v0.2.0 extends the v0.1.0 human-operated documentation baseline with
machine-checkable minimum-adoption contracts. Adopters must own their
instantiated records, replace every placeholder with verified project facts,
select an immutable AFEF revision, and preserve the existing authority,
separation, evidence, review, and final-gate boundaries.

The validator checks the recorded pin's shape but does not authenticate it or
compare it with the framework checkout. Follow the
[validation guide](../validation.md) for supported record locations, invocation,
diagnostics, and claims boundaries.

## Non-Goals and Claims Boundary

AFEF remains a human-operated engineering and governance framework. It is not an
agent runtime, product runtime, workflow engine, project generator, general CLI,
reusable GitHub Action, automatic authorization system, or production
deployment. Validation confirms represented record conformance only. It cannot
prove factual truth, real-world or cryptographic human identity, separation of
control, approval authenticity, continuing authority, real-world execution,
production readiness, publication, deployment, or real-project adoption.

AFEF does not approve, authorize, execute, publish, repair, or automatically
create or modify adopter records. A version declaration or framework publication
does not establish adoption by GitHub Steward.

Verify actual publication and release state from the designated repository's
default branch, the applicable annotated Git refs, and GitHub Release metadata.
